# Glyphite — project guide for Claude Code

## What this is

**Glyphite** is a 2D game engine that renders *only* the 95 printable ASCII characters (codes 32–126),
each in its own colour. It runs in the browser as a single self-contained HTML page. Its focus is
physics and lighting:
- a destructible voxel world with falling sand,
- rigid bodies, and structures that break where they are hit,
- ray-traced sun and spot lights,
- particles and visual effects,
- an NES-style sound chip that plays MIDI.

**Regolith Lander** is the test game we build on top of it: a moon-lander game used to prove and drive
the engine.

**The goal:** turn this code into a complete, game-agnostic engine called Glyphite, one that works for
*any* 2D game. The lander stays as the reference/test game. Today engine and game still live in one
codebase and share globals. Separating them is planned work; see `docs/ROADMAP.md`. Until the user asks
for that refactor, keep changes scoped to what is requested.

Read these before larger work:
- `docs/HISTORY.md`: every request so far and what was built, in order.
- `docs/ARCHITECTURE.md`: how every subsystem works (units, world, physics, light, rendering, audio).
- `docs/LESSONS.md`: bugs we hit, why things are the way they are, pitfalls to avoid.
- `docs/ROADMAP.md`: the engine plan and the known-issue backlog.
- `docs/TESTING.md`: the test scripts and how to run them.

## Layout

```
build.sh              concatenates src/* (in a fixed order) -> dist/regolith.html (+ dist/test.html)
src/00_head.html      page shell: CSS, canvas, title-bar buttons, touch controls, <script> opening
src/01_core.js        ENGINE  units, detail scale (RES), materials, world grid, granular sand CA, heat
src/02_particles.js   ENGINE  particle system (SoA), deposit, explode(), FX state (shake, rings, lights, texts)
src/03_body.js        ENGINE  rigid body vs voxel grid (impulse contacts, friction, hull point kinds)
src/04_light.js       ENGINE  lighting: occupancy, summed-area tables, sun sweep, point/cone lights, AO, soak
src/05_render_base.js ENGINE  renderer: WebGL glyph-atlas shader + 2D canvas fallback, HUD grid, layers
src/06_render_scene.js ENGINE scene shading -> glyph+colour per cell; sky layer (stars, Earth)
src/07_audio_input.js ENGINE  procedural SFX (Sfx) and input (keys, mouse aim, touch)
src/07b_chip.js       ENGINE  "Chip": NES 2A03-style synth + Standard MIDI File parser + Web MIDI input
src/07c_songs.js      GAME    soundtrack as base64 MIDI (generated by tools/compose.py)
src/08_level.js       GAME    landing-site generator (terrain, craters, caves, pads, lamps, roof, ice, settling)
src/09_game_sim.js    GAME    lander physics (spring-damper legs), rockets, meteoroids, contacts, scoring
src/09b_boulders.js   GAME    boulders (round rigid bodies)
src/09c_chunks.js     ENGINE+GAME breakable structures (support check, chunks, freeze), island settling, lamp hooks
src/10_game_view.js   GAME    lights gathering, world extras (lamps, pads, rockets), HUD, title, messages
src/10a_lander_data.js GAME   lander pixel-art sprite (48x50, palette-indexed; generated by tools/art.py)
src/10a_lander_art.js GAME    draws the lander from its sprite as ASCII (rotation, sliding legs, lighting)
src/10b_music.js      GAME    music director, MIDI file loading/drag-drop, MIDI IN, chip meters
src/11_main.js        GAME    state machine, update/draw loop, detail switching, keys, boot
tools/                sprite2ascii.py (pixel art -> sprite data), ascii_preview.py (offline ASCII preview of a sprite),
                      art.py (the lander's hand-tuned sprite), compose.py (soundtrack), render_songs.js (songs -> WAV)
tests/                Playwright (Python) checks, synchronous physics probes, profilers
ref/                  reference art (ref/lander_ref.png)
music/                the soundtrack as .mid files
docs/                 documentation + images
.claude/skills/       project skills (see below)
```

The banner comment at the top of each part (`// ===================== ENGINE · ... =====`) says
whether it belongs to the engine or the game.

## Commands

```sh
./build.sh                                   # -> dist/regolith.html, dist/test.html; prints SYNTAX_OK
python3 tests/dbg_legs.py 2                  # landing physics sweep at detail 2 (fast, synchronous)
python3 tests/test18.py 2d                   # lander renders (landed/tilted) at detail 1-3 -> shots/
python3 tests/test16.py gl 2d                # real-time smoke test in both renderers
python3 tools/sprite2ascii.py ref/x.png --name x   # pixel art -> src/x_sprite.js + shots/x_preview.png
python3 tools/ascii_preview.py src/x_sprite.js --k 0.28 --res 1,2,3   # see it as ASCII in 0.2 s, no browser
python3 tools/compose.py                     # regenerate soundtrack -> music/*.mid, src/07c_songs.js
```
Open `dist/regolith.html` (or `dist/test.html`) in a browser to play. `#gl` / `#2d` in the URL forces
a renderer. Requirements for tests: Python 3, `pip install playwright pillow numpy`,
`playwright install chromium`, and Node (for `node --check` in build.sh).

## Rules of the codebase

- **Output is printable ASCII only.** Every glyph written to the world or HUD grid must be 32–126.
  Glyph code 0 in the world grid means "empty, let the sky show through"; 32 is an opaque blank.
- **Single file.** The shipped game is one HTML file with no runtime dependencies. The only external
  request is the Google Fonts stylesheet for JetBrains Mono, with a monospace fallback.
- **Units.** A cell is 1 unit wide and 2 units tall (`ASPECT = 2`). Detail scale `RES` ∈ {1, 1.5, 2,
  2.5, 3}. Author every physical size and speed in *base units* and multiply by `RES` (often aliased
  `S`). `UNIT_M = 0.5/RES` metres per unit and `G = 1.62/UNIT_M`. A finer detail level adds
  characters; it does not zoom out.
- **Same world at every detail level.** Levels are generated in base units, so behaviour must match
  at RES 1–3. Test physics changes at several RES values.
- **Both renderers.** WebGL is the main path. The 2D canvas is the fallback, and it is also chosen
  automatically when WebGL is software-emulated. Visual changes must work in both.
- Code style: compact modern JS, `'use strict'`, no frameworks. Comments explain *why* in plain
  language; keep the existing banner and section-comment style. Don't add dead code; delete what
  you replace.
- Keep `docs/` current when you change behaviour: add to HISTORY, LESSONS and ROADMAP as relevant.

## How to verify work (always, before saying something is done)

1. `./build.sh` must print `SYNTAX_OK`.
2. Run focused synchronous checks with `page.evaluate`. Step the sim with `update(DT)` in a loop; it
   is deterministic enough and fast. Real-time headless frames are slow (~70 ms in software GL), so
   don't wait on wall-clock time for physics.
3. Take screenshots at detail 1, 2 and 3 in both renderers:
   - Freeze the loop with `window.update = () => {}`; don't use the pause state, which draws a PAUSED box.
   - Zoom with `device_scale_factor=3` and a clip around the object.
   - Build contact sheets with Pillow and look at them.
4. Run the relevant regression scripts from `docs/TESTING.md` and check for page errors.
The `glyphite-verify` skill walks through this loop.

## Skills in this repo

- `glyphite-pixel-art-to-ascii`: convert a pixel-art image into an ASCII sprite for a Glyphite game.
  It ends with a self-review that improves the skill.
- `glyphite-verify`: the build → probe → screenshot → regression loop for any engine or game change.
